# 우주민턴 온라인

React + Supabase 기반 동호회 모임 예약과 경기 운영 앱. 기존 GitHub Pages 배포를 유지합니다.

## 기능

- 이름 / 성별 / 아이디 / 비밀번호 가입, 관리자·일반 회원 권한
- 월별 달력, 관리자 모임 등록·취소
- 정원 내 참석 신청, 초과 시 선착순 대기, 취소 시 자동 승격
- 한국 시간 기준 당일 관리자 경기 운영, 모임별 경기 저장
- 일반 회원의 현재 코트·경기 대기 팀 입장 순서·미편성 대기 인원·내 경기 상태 조회, 15초 주기 갱신
- 일반 회원은 모임 상세 하단에서 한 번 쉬기·경기 제외 요청 및 취소 가능. 운영자는 경기 운영 화면에서 승인·반려
- 경기 저장 시 버전 검사: 다른 관리자의 변경을 조용히 덮어쓰지 않음

## 최초 연결

1. Supabase 프로젝트를 생성합니다.
2. SQL Editor에서 `supabase/schema.sql` 전체를 한 번 실행합니다. 신규 프로젝트용 스키마입니다. 이어서 `supabase/migrations/20261030_game_requests.sql`을 실행합니다. **이미 운영 중인 프로젝트는 schema.sql을 다시 실행하지 말고 이 migration 파일만 실행하세요.**
3. Auth 설정에서 Email provider를 사용하고 **Confirm email을 끕니다**. 아이디를 `아이디@members.invalid`라는 내부 인증 식별자로 변환하므로 실제 이메일을 수집하거나 발송하지 않습니다. 로그인 아이디는 영문·숫자·밑줄 4~24자이며 대소문자를 구별하지 않습니다. 비밀번호 최소 길이를 8자로 설정하세요. 운영 시 가입 남용 방지를 위한 Auth rate limit을 확인하세요.
4. `.env.example`을 `.env.local`로 복사하고 프로젝트 URL, **publishable 공개 키**를 입력합니다 (`REACT_APP_SUPABASE_PUBLISHABLE_KEY`). 기존 `REACT_APP_SUPABASE_ANON_KEY` 이름도 호환됩니다. `service_role` / secret 키는 절대 브라우저에 넣지 마세요.
5. `npm ci`, `npm start`로 실행합니다.
6. 최초 관리자 계정을 일반 회원으로 가입한 후 SQL Editor에서 다음을 실행합니다.

```sql
update public.profiles set role = 'admin' where username = '관리자아이디';
```

추가 관리자도 프로젝트 소유자가 같은 SQL로 지정합니다. 앱 회원이 자기 역할을 변경할 권한은 없습니다. 이름·성별·아이디는 본인과 관리자만 조회할 수 있고, 모임 명단 API에는 참석자의 이름만 노출합니다.

## 배포

`.env.local` 설정 후 `npm run build`, `npm run deploy`로 기존 GitHub Pages에 배포합니다. 환경변수는 빌드 시 포함되므로 변경 후 다시 빌드하세요. CI에서 배포하면 같은 이름의 환경변수를 CI에도 설정해야 합니다. 데이터베이스 설정 전 배포하면 서비스 연결 준비 화면이 표시됩니다.

`npm test -- --watchAll=false`로 UI 기본 화면·한국 날짜 경계·로그인 아이디 정규화를 검사합니다.

`npm run test:database`는 PGlite의 실제 PostgreSQL 엔진과 Auth 테스트 스텁으로 SQL 스키마·권한·정원·대기 승격·재신청 순서·모임 취소·경기 날짜 및 저장 충돌을 검사합니다. 실제 Supabase Auth 및 동시 요청 부하 검증은 연결 후 별도로 수행하세요.

## 운영 규칙

- 모임 시작 시각 이후 신규 신청은 마감됩니다. 기존 신청 취소와 대기 승격은 가능합니다.
- 신청/취소/모임 취소/경기 저장은 같은 모임 행을 잠가 순서대로 처리합니다. 클라이언트의 정원 표시와 관계없이 서버가 최종 판단합니다.
- 취소 후 재신청하면 대기 순서는 맨 뒤입니다.
- 경기 운영은 한국 시간 기준 해당 날짜에만 서버에서 허용합니다.
- 경기 운영을 열 때 해당 모임의 확정 참석자를 대기 인원에 불러옵니다. 예약 대기자는 제외하며 이미 코트·대기 팀·우선 대기에 있는 회원은 중복 추가하지 않습니다. 저장한 배치와 경기 수를 유지하며 새 확정 참석자를 추가합니다. 운영 화면을 열어 둔 동안의 참석 변동은 다시 열 때 반영됩니다. 취소된 회원은 미배정 대기 명단에서 제외하되 진행 중 코트와 대기 팀은 유지합니다.
- 대기 인원의 ‘삭제’는 이번 모임 경기에서 제외하는 동작입니다. 제외 목록을 경기 상태에 저장하므로 다시 열어도 재추가하지 않으며, ‘경기 제외’ 목록의 ‘다시 참여’로 복구할 수 있습니다. 제외·복구는 자동 저장됩니다. 회원 계정과 참석 신청, 누적 경기 수는 유지합니다.
- 새 모바일 경기 운영 화면에는 성별·경기 수를 표시합니다. 선수 선택 후 빈자리 또는 교체할 선수를 눌러 배치할 수 있습니다. 관리자 권한으로 회원 성별을 조회하므로 별도의 SQL 변경은 필요하지 않습니다.
- **팀 편성·선수 이동(교체 포함)·경기 종료 결과를 자동 저장**합니다. 저장 중·완료·실패 상태를 표시하며 실패하면 화면의 결과를 유지하고 수동으로 재시도할 수 있습니다. 코트 설정 등 다른 변경은 ‘경기 저장’을 눌러 저장합니다. 저장 충돌 시 화면의 변경을 확인한 뒤 모임으로 돌아가 다시 여세요. 다른 관리자의 저장과 충돌하면 자신의 변경이 저장되지 않습니다.
- 기존 브라우저의 `badminton_state_v1` 기록은 가져오지 않습니다. 새 온라인 모임마다 별도 경기 기록을 만듭니다.
- 비밀번호 분실 시 프로젝트 소유자가 Supabase 관리 환경 또는 서버 전용 Admin API로 본인 확인 후 재설정해야 합니다. 앱 내 관리자 비밀번호 초기화·관리자 지정 UI는 포함하지 않았습니다. 실제 이메일이 없으므로 이메일 복구는 사용할 수 없습니다.
- 현재 범위에는 현장 도착 체크, 모임 수정, 푸시 알림, 오프라인 운영은 포함하지 않습니다.

## 권한 검증

실서비스 연결 후 일반 회원과 관리자 계정을 각각 만들어 다음을 확인하세요.

1. 일반 회원은 모임 생성·취소·경기 저장 API를 직접 요청해도 거절됩니다.
2. 정원 1명 모임에 두 회원이 동시에 신청하면 참석 1명·대기 1명이 됩니다.
3. 참석자 취소 시 첫 대기자가 승격됩니다. 대기 취소 후 재신청은 뒤로 이동합니다.
4. 두 관리자 창에서 같은 경기 버전을 저장하면 두 번째 저장은 거절됩니다.
5. 어제/내일 모임의 경기 저장은 서버에서도 거절됩니다.

스키마와 RLS 정책을 실제 Supabase에 적용하고 위 검증을 마친 뒤 회원에게 배포하세요.

## 회원 경기 요청 기능 활성화

기존 프로젝트는 `supabase/migrations/20261030_game_requests.sql`을 SQL Editor에서 실행해야 합니다. 파일은 기존 데이터를 삭제하지 않으며 재실행할 수 있습니다. 테이블이 없을 때 화면은 기존 기능을 유지하고 요청 버튼만 준비 중으로 표시합니다.

- 모임 당일, 참석 확정자만 경기 운영 시작 후 요청할 수 있습니다.
- 대기 중인 요청은 회원별로 한 건만 허용하며, 회원은 본인 요청만 조회·취소할 수 있습니다.
- 관리자에게 15초 주기로 요청이 표시됩니다. 경기 운영 화면에서 승인·반려합니다.
- 코트·대기 팀 배정 중인 회원은 대기 인원으로 돌아온 후 승인할 수 있습니다.
- 승인 시 경기 상태 변경·버전 증가·요청 처리 상태를 하나의 트랜잭션으로 저장합니다. 충돌하면 모두 취소되고 요청은 확인 대기 상태로 유지됩니다.
- 요청 승인·반려는 회원 계정이나 모임 참석 신청 상태를 변경하지 않습니다.

`npm run test:requests`로 PostgreSQL 엔진에서 요청 권한, 중복 방지, 취소, 승인·반려, 경기 상태 변경과 저장 충돌 롤백을 검사합니다.

## 계정관리 · 가입 승인 · 월간 참석 랭킹 활성화

운영 중인 프로젝트에서는 다음 순서로 설정합니다.

1. 기존 요청 기능 SQL 적용 후 `supabase/migrations/20261030_accounts_and_statistics.sql` 전체를 SQL Editor에서 실행합니다. 기존 회원은 승인 상태를 유지하고, 이후 가입자는 일반 회원·승인 대기로 생성됩니다. 회원 메타데이터로 본인이 관리자나 승인 상태를 지정할 수 없습니다.
2. Supabase **Authentication → Hooks → Custom Access Token**에서 Postgres 함수 **`public.approval_access_token_hook`**를 선택하고 활성화합니다. 이 단계가 서버의 비밀번호 로그인·토큰 갱신 차단에 필요합니다. SQL 적용만으로도 승인 전 계정의 데이터 접근은 차단되지만, Auth 토큰 발급 자체를 막으려면 훅 설정까지 완료해야 합니다.
3. 관리자 계정으로 로그인해 **계정관리**에서 가입 승인·관리자 전환·계정 삭제를 사용합니다. 모든 승인 회원은 **통계**에서 이번 달 참석 랭킹을 봅니다.

가입 신청은 메인 앱과 분리한 비영속 인증 클라이언트에서 처리하며 자동 로그인하지 않습니다. Auth 훅은 가입 처리가 끝나도록 `email/signup`에만 데이터 접근이 불가능한 anon 토큰을 허용하고, 승인 전 비밀번호 로그인과 갱신은 거절합니다.

- 본인 계정 삭제·본인 권한 변경은 막습니다. 승인·권한 변경·삭제를 같은 DB 잠금으로 순서대로 처리해 마지막 관리자 보호와 동시 권한 변경을 검사합니다.
- 계정 삭제는 로그인 계정과 프로필을 삭제합니다. 연결된 참석·요청 기록을 정리하고 빈자리는 대기순으로 승격합니다. 모임 생성자는 null로 남기고 기존 경기의 선수 정보는 ‘삭제된 회원’으로 익명화합니다. 영향을 받은 경기 버전을 증가시켜 오래된 운영 화면의 저장으로 개인 정보가 복구되지 않게 합니다.
- 랭킹은 한국 시간 기준 해당 월에 시작한 모임의 참석 확정 기록을 집계합니다. 취소·미래 모임과 참석 대기자는 제외합니다. 실제 현장 출석을 별도로 체크한 수치는 아닙니다. 같은 횟수는 공동 순위입니다.
- SQL 설정 전에는 계정관리·통계에 설정 필요 안내가 표시되고 신규 가입 신청은 제한됩니다. 기존 회원 로그인과 모임 기능은 유지합니다.

`npm run test:accounts`는 실제 PostgreSQL 엔진과 Auth 스텁에서 위 권한·승인·삭제·익명화·랭킹·훅 반환값을 검사합니다. Supabase Auth에서 훅이 실제로 호출되는 로그인 동작은 설정 완료 후 승인 대기 계정으로 확인해야 합니다.
